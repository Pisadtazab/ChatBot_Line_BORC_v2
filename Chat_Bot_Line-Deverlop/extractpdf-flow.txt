extractPDF.py: PDF upload and RAG ingestion flow
=================================================

Purpose
-------
`app/routers/extractPDF.py` receives a PDF, turns its pages and images into
searchable records, creates a Thai document summary using the Typhoon LLM,
and stores the searchable records in MongoDB. Images are uploaded to
Cloudinary, while MongoDB stores the image URL and related metadata.
It does not answer chat messages itself.

Startup
-------
When FastAPI imports this router, the file loads:
- BAAI/bge-m3: creates embeddings for PDF text and image descriptions.
- Typhoon LLM: creates a Thai document summary.
- The selected configuration for the embedding service.

Upload flow: POST /upload_pdf
------------------------------

  Client uploads a .pdf
          |
          v
  Validate filename ends with .pdf
          |
          v
  Save to a unique temporary PDF in app/src/ (50 MB maximum)
          |
          v
  extract_pdf_content(save_path)
          |
          +--> Open PDF with PyMuPDF
          |       |
          |       +--> For every page
          |       |       |
          |       |       +--> Extract and clean text with FixThaiPDF
          |       |       +--> Extract clickable HTTP/HTTPS links with PyMuPDF
          |       |       +--> Add extracted URLs to the same page text chunk
          |       |       +--> Extract images and create a text-context description
          |       |       +--> Add image placeholders to that page's text
          |       |       +--> Build one content chunk for the page
          |       |
          |       +--> Combine all page text
          |       +--> Tokenize Thai text when Thai characters exist
          |       +--> summarize_content(...)
          |               |
          |               +--> Send document text to Typhoon LLM
          |               +--> Typhoon generates a Thai document summary
          |
          +--> Returns: (content_chunks, summary)
          |
          v
  store_in_mongodb(content_chunks, filename)
          |
          +--> For every text chunk
          |       +--> Create BAAI/bge-m3 embedding
          |       +--> Store content, metadata, and embedding in MongoDB
          |
          +--> For every extracted image
                  |
                  +--> Upload original image bytes to Cloudinary
                  |       |
                  |       +--> Returns image_url
                  |
                  +--> Create BAAI/bge-m3 embedding
                  |   from the image description
                  |
                  +--> Store image description, metadata,
                      image_url, and embedding in MongoDB
          |
          +--> Remove temporary PDF
          |
          v
  Return JSON: message + summary

Example response
----------------
{
  "message": "research.pdf uploaded and processed",
  "summary": "Generated Thai summary"
}

----------------------------

      MongoDB Vector Search
              |
        +-----+-----+
        |           |
        v           v
   Text results  Image results
        |           |
        |           +--> image_url from MongoDB
        |
        v

        v

        |
        +--------------------+
        |                    |
        v                    v
   Text response       image_results
                             |
                             v
                        LINE response
                      (Text + Images)

The document summary is generated by Typhoon during PDF upload and is returned
to the caller of /upload_pdf. It is not currently stored as a vector-search
record and is not sent to Typhoon again when answering a chat message.

For chat RAG, the system searches the stored page text and image description
records using MongoDB Vector Search. The retrieved text is provided to
Typhoon to generate the chat answer, while image results provide the
Cloudinary image URLs that are sent to LINE.

Images are not stored as binary data in MongoDB. The original image is stored
in Cloudinary, and MongoDB stores the Cloudinary image_url together with the
image description, metadata, and embedding.

The current image description is a heuristic made from the page number and
nearby page text; it does not analyze the image pixels.


Detailed ingestion flow
-----------------------

The PDF ingestion process can be separated into two main responsibilities:

1. Extract and prepare information from the PDF.
2. Convert the extracted information into searchable records in MongoDB.

The overall flow is:

Text extraction flow
--------------------

For each PDF page, text is extracted and cleaned before it is stored.

  PDF Page
      |
      v
  PyMuPDF
      |
      v
  Raw page text
      |
      v
  FixThaiPDF
      |
      v
  Cleaned text
      |
      v
  Add image placeholders
      |
      v
  Page content chunk

The page content is kept as a searchable text record. This content is later
used as part of the context returned by MongoDB Vector Search.

Clickable HTTP and HTTPS links are extracted from each page with PyMuPDF's
link annotations. Their URLs are appended to that page's text chunk before the
text embedding is created, so a retrieved advisor record can provide source
links to the chat answer. Links are only available for PDFs that contain
extractable link annotations or URLs in their page text.


Image extraction flow
---------------------

Images are handled separately from normal page text.

  PDF Page
      |
      v
  Extract image bytes
      |
      v
  Generate image description
      |
      v
  Create image metadata
      |
      +--------------------------+
      |                          |
      v                          v
  Upload image              Create embedding
  to Cloudinary              from image
      |                       description
      v                          |
  image_url                       |
      |                          |
      +-------------+------------+
                    |
                    v
             Store in MongoDB

MongoDB does not store the original image binary.

Instead, MongoDB stores information that allows the RAG system to find and
use the image:

  {
      "content": "image description",
      "metadata": {
          "type": "image",
          "source": "research.pdf",
          "page": 5,
          "chunk_page": 5,
          "content_type": "image",
          "image_url": "https://res.cloudinary.com/..."
      },
      "embedding": [...]
  }


Embedding flow
--------------

Both text records and image-description records are converted into vectors
using BAAI/bge-m3.

  Text
   |
   v
  BAAI/bge-m3
   |
   v
  Text embedding
   |
   v
  MongoDB


  Image description
   |
   v
  BAAI/bge-m3
   |
   v
  Image embedding
   |
   v
  MongoDB

This allows MongoDB Vector Search to search both normal document content and
image descriptions using the same embedding model.


Document summary flow
---------------------

The document summary is generated separately from the vector-search records.

  All extracted page text
           |
           v
      Clean / prepare
           |
           v
     Thai tokenization
           |
           v
   summarize_content()
           |
           v
      Typhoon LLM
           |
           v
    Thai document summary
           |
           v
      API response

The summary is generated once during PDF upload.

The summary is not currently inserted into MongoDB as a vector-search record.

Therefore:

  PDF upload
       |
       +--> Summary
       |      |
       |      +--> Returned to /upload_pdf caller
       |
       +--> Searchable records
              |
              +--> Stored in MongoDB
              |
              +--> Used later by chat RAG

Image selection flow during RAG
-------------------------------

Image URLs are not generated by the LLM.

The image URL must already exist in the MongoDB context.

  MongoDB
     |
     v
  Image result
     |
     +--> image_url
     |
     v
  RAG context
     |
     v
  Typhoon LLM
     |
     v
  Select relevant image_urls
     |
     v
  Validate selected URLs
     |
     v
  image_results
     |
     v
  LINE


LINE image limitation
----------------------

The RAG layer can return multiple relevant image URLs.

The LINE response layer handles the platform message limit.

  image_results
       |
       v
  Count images
       |
       +----------------------+
       |                      |
       v                      v
   1 - 4 images          More than 4 images
       |                      |
       v                      v
  Send text + images     Do not send images
                              |
                              v
                         Send text explaining
                         that the images exceed
                         the LINE message limit

The limitation is therefore handled when constructing the LINE response,
rather than limiting the number of relevant images during MongoDB retrieval.

Key responsibilities
--------------------

extractPDF.py
-------------
- Receive PDF uploads.
- Validate PDF files.
- Extract text from PDF pages.
- Clean extracted Thai text.
- Extract images from PDF pages.
- Create image descriptions.
- Create embeddings for searchable content.
- Upload original images to Cloudinary.
- Store searchable records in MongoDB.
- Generate the document summary using Typhoon.
- Return upload status and document summary.

MongoDB
-------
- Stores searchable text records.
- Stores image-description records.
- Stores embeddings.
- Stores document metadata.
- Stores Cloudinary image URLs.
- Provides Vector Search during RAG.

Cloudinary
----------
- Stores original extracted images.
- Provides public image URLs.
- MongoDB stores the URL instead of the binary image.

query_rag()
-----------
- Converts the user's question into an embedding.
- Searches MongoDB Vector Search.
- Retrieves relevant text and image records.
- Builds context for Typhoon.
- Generates the chat answer.
- Selects relevant image URLs from the retrieved context.
- Validates selected image URLs against the retrieved MongoDB records.

LINE Bot
--------
- Receives the final answer from the RAG layer.
- Sends the text response.
- Sends relevant images when the number of images is within the LINE message
  limit.
- If too many images are found, sends the text response without images and
  informs the user about the limitation.


Research-ready workflow description (Thai)
------------------------------------------

ระบบแบ่งการทำงานเป็นสองช่วง ได้แก่ การเตรียมเอกสารสำหรับค้นคืน และการ
ตอบคำถามจากข้อมูลที่ค้นคืนได้ โดยมี FastAPI เป็นจุดรับคำขอ, MongoDB เป็น
ฐานข้อมูลสำหรับค้นคืนแบบเวกเตอร์, Hugging Face Inference API สำหรับสร้าง
embedding, Typhoon API สำหรับสรุปและสร้างคำตอบ และ Cloudinary สำหรับจัดเก็บ
ไฟล์รูปภาพที่แยกจาก PDF

1. การรับและตรวจสอบเอกสาร: ผู้ใช้ส่งไฟล์ PDF ผ่าน `POST /upload_pdf` ระบบ
   ตรวจนามสกุลไฟล์ ตรวจขนาดไม่เกิน 50 MB และตรวจลายเซ็น `%PDF-` ก่อนบันทึก
   ลงไฟล์ชั่วคราวเพื่อประมวลผล
2. การแยกข้อมูลรายหน้า: PyMuPDF อ่านข้อความและลิงก์ HTTP/HTTPS ที่ฝังอยู่ใน
   แต่ละหน้า จากนั้นทำความสะอาดข้อความด้วย FixThaiPDF แล้วนำ URL ที่พบมา
   ต่อท้ายข้อความของหน้าเดียวกัน เพื่อให้ทั้งเนื้อหาและลิงก์อยู่ในระเบียนที่
   ค้นคืนร่วมกันได้
3. การแยกรูปภาพ: ระบบดึงข้อมูลไบต์ของรูปจาก PDF และสร้างคำอธิบายจากหมายเลข
   หน้าและข้อความใกล้เคียง คำอธิบายนี้เป็นข้อมูลประกอบจากข้อความ ไม่ใช่ผล
   วิเคราะห์เนื้อหาพิกเซลของรูป จากนั้นใส่ placeholder รูปในข้อความของหน้า
4. การจัดทำสรุป: ระบบรวมข้อความจากเอกสารและส่งให้ Typhoon API เพื่อสรุป
   ภาษาไทย โดยสรุปถูกส่งกลับในผลตอบรับของ API อัปโหลด แต่ไม่ได้บันทึกเป็น
   ระเบียนสำหรับ Vector Search
5. การสร้างระเบียนค้นคืน: ระบบสร้าง embedding ของข้อความแต่ละหน้าและคำอธิบาย
   รูปด้วย BAAI/bge-m3 แล้วบันทึกเนื้อหา embedding และ metadata ลง MongoDB
   รูปต้นฉบับอัปโหลดไป Cloudinary และ MongoDB เก็บ URL ของรูปแทนไบต์รูป
6. การตอบคำถาม: เมื่อได้รับข้อความจาก LINE ระบบสร้าง embedding ของคำถาม
   ค้นระเบียนที่เกี่ยวข้องผ่าน MongoDB Vector Search (พิจารณา 80 candidates
   และส่งผลลัพธ์ที่เกี่ยวข้องสูงสุด 8 รายการ) แล้วประกอบเนื้อหาและ URL รูปที่
   ค้นพบเป็น context ให้ Typhoon สร้างคำตอบและเลือก URL รูปจากรายการที่ค้นพบ
   เท่านั้น
7. การอ้างอิงอาจารย์: เมื่อถามเจาะจงอาจารย์ ระบบกำหนดให้ตอบจาก context
   และแนบ URL อ้างอิงที่เกี่ยวข้องซึ่งอยู่ใน context หากเอกสารไม่มี URL ระบบ
   ไม่สร้างลิงก์ขึ้นเอง ลิงก์ที่ฝังใน PDF จะถูกนำมาใช้ได้เมื่อระบบแยก URL นั้น
   ได้และเนื้อหาที่เกี่ยวข้องถูกค้นคืนมาใน context
8. การส่งคำตอบ: LINE Bot ส่งข้อความคำตอบพร้อมรูปที่ผ่านการตรวจ URL กับข้อมูล
   ใน MongoDB จำกัดรวมไม่เกิน 5 ข้อความต่อ push (ข้อความ 1 รายการและรูปได้
   สูงสุด 4 รายการ) หากรูปที่เลือกมีมากกว่า 4 รูป ระบบส่งข้อความแจ้งข้อจำกัด
   โดยไม่ส่งรูปชุดนั้น

ดังนั้นคำตอบและการอ้างอิงขึ้นกับข้อมูลที่แยกและค้นคืนได้จากเอกสาร ส่วน
การแสดงรูปขึ้นกับ URL ที่บันทึกใน MongoDB และข้อจำกัดจำนวนข้อความของ LINE


Important distinction
---------------------

`extractPDF.py` is responsible for ingestion, not chat.

The responsibilities are separated as follows:

  PDF
   |
   v
extractPDF.py
   |
   v
Searchable MongoDB records
   |
   v
query_rag()
   |
   v
Typhoon
   |
   v
LINE Bot

The document summary created during PDF upload is independent from the
chat-answer generation.

The PDF summary is generated once during ingestion and returned by
`POST /upload_pdf`.

The chat answer is generated later from MongoDB Vector Search results when
the user asks a question.

The original PDF is not sent to Typhoon again during normal chat RAG.

The original images are not stored in MongoDB. Cloudinary stores the image
files, while MongoDB stores the image URL, image description, metadata, and
embedding required for retrieval.
